## What this does

Locks **option (a)**, corrected per the operator's framing:

- The folder-backend (S04) does NOT produce a finished knowledge article. It
  produces **source material**: the topic-focused answer/extract derived from
  the read file (P2 still holds -- the raw file *body* never persists, only the
  derived extract relevant to the curiosity topic).
- The backend writes that extract to `raw/` mirroring the **email-deep-scan**
  landing (email backend writes `deep-<slug>.md` to raw/; folder backend writes
  the analogous answer artifact). The exact subfolder is pinned in this task by
  reading where the email backend lands its `deep-<slug>.md` and choosing a
  sibling (e.g. `raw/answers/answer-<slug>.md`), with provenance frontmatter:
  source file path, topic, request id, as-of (source mtime).
- On the **next `compile` pass**, compile sees the new source and distills it
  into `knowledge/` exactly as it does every other source -- entity/fact pages,
  wikilinks, dedup, all via the established compile knowledge-writer. This is
  the symmetry the operator wants: compile *generates* the curiosity request
  (post-compile producer pass) AND later *consumes* the answer.
- **Single knowledge-writer = compile.** No direct knowledge-write from the
  backend (no 3-layer-scope collision). No "double-distill": the backend
  extracts, it does not finalize; compile is the only distill-to-knowledge step.

Document explicitly in the DECISIONS entry, for S03/S04/S05:
- the `raw/` landing path + filename pattern + provenance frontmatter,
- that the artifact is a normal compile source (no compile-skip; it SHOULD be
  distilled) -- contrast with index files (which ARE compile-skip metadata),
- the staleness handle (source mtime carried so a later change can re-trigger),
- a note refining DECISIONS 2026-06-07 P2 wording (the folder backend's landing
  is the SAME as email's raw/-then-compile, not a separate "answer-only-no-raw"
  contract; "no raw body" = no full file body, the derived extract is allowed).
