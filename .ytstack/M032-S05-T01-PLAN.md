## What this does

The listener status knows only the newest chunk per channel, which is enough for "recording / check" but not for a timeline. `audio_chunks` keeps one row per ~30 s chunk with an ISO timestamp and a channel-bearing `file_path`, so the history is already on disk; this task reads it the same way freshness is read (the `sqlite3` CLI, read-only, safe beside the WAL writer) and turns it into fixed hourly bins the Overview's heat strip can draw without any further derivation. The SQL returns epoch ms; all bucketing happens in a pure function with an injectable clock, so the shape (alignment, window, boundary) is pinned by unit tests and the I/O wrapper stays a dozen lines. The IPC mirrors `status()`: one `invoke` per request, no polling, no caching (720 rows × 2 channels is a few ms).
