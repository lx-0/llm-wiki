# M033-S05-T01 -- Task Plan

**Summary:** Type-checker probe and decision. Install the candidates, run each in `basic` mode
on `scripts/core/` and on all of `scripts/`, record findings and wall time, pick one (CONTEXT
open question 1), remove the others, write the DECISIONS entry, and put the config in
`pyproject.toml`.

## Files

- Modify: `pyproject.toml` — a `typecheck` dependency group (the winner, pinned exactly, like
  `lint`'s ruff) and its `[tool.<checker>]` section: Python 3.12, the `.venv`, `scripts` +
  `hooks` as search roots (the engine imports `core.*` from the `scripts/` source root), basic
  strictness, scope `scripts/core/` for the gate.
- Modify: `uv.lock` — written by `uv add` / `uv remove`, never by hand.
- Modify: `.ytstack/DECISIONS.md` — one entry with the measurement table, the choice and why.
- Create (throwaway, outside the repo): `/tmp/t01-typecheck-probe.sh` and per-candidate
  configs in `/tmp`, so no loser's config ever lands in the repo.

## What this does

Two facts measured before planning change the task line slightly.

1. **A `typecheck` group, not `--dev`.** `wiki update` and `install.sh` run a bare
   `uv sync`, which installs the default groups, and `dev` is one of them. A checker in `dev`
   would land in every operator vault's venv. It goes into its own group, the way `lint`
   keeps ruff out (CI: `uv sync --group lint`).
2. **Three candidates, not two.** pyright is published on npm only; its PyPI `pyright`
   package is a wrapper that downloads Node on first run. `basedpyright` is the same checker
   packaged for PyPI with Node bundled, so it is probed as the third way to get pyright into
   pre-commit and CI. ty is Astral's checker and still a beta (0.0.86, 2026-10-09; 1.0 is
   targeted for 2026 but has not shipped).

The probe, per candidate:

- **Install:** `uv add --group typecheck pyright basedpyright ty` (current versions,
  recorded).
- **Config:** a probe config in `/tmp`. Basic mode for pyright and basedpyright, set
  explicitly because basedpyright defaults to `all`. ty has no modes, so it runs on its
  default rules. The search paths are `scripts` + `hooks`, Python 3.12 is from `.venv`, and
  the import-resolution check runs first: unresolved `core.*` imports would make every count
  meaningless.
- **Counts:** errors and warnings per rule, on `scripts/core/` (35 files) and on all of
  `scripts/` (208 files).
- **Wall time:** three runs each, median, warm cache.
- **Sample triage:** 20 findings per candidate on `core/`, read against the code. Each is
  real (a local fix exists), a stub gap (dependency untyped), or noise (checker
  limitation). Under the CONTEXT criterion, the gate goes to the checker whose `basic` mode
  is green-able within the slice.
- **Integration cost:** Node needed or not, install size, first-run network access, and how
  stable its diagnostics are across versions (a 0.0.x tool can change them in a patch
  release, so the pin matters).

Decision: the winner stays in `typecheck`, pinned exactly; the others are removed with
`uv remove`. Its `[tool.…]` section is committed, and its count on `core/` under the committed
config matches the probe. The DECISIONS entry records the table, the triage and the choice.
The gate itself (green `core/`, pre-commit, CI) is T02.
