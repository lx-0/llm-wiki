# Design: Remote MCP access to llm-wiki

Generated by ytstack:office-hours on 2026-08-24
Branch: main
Repo: lx-0/llm-wiki
Status: ACTIVE — lane D confirmed by operator action (meinkontext producer contract v0.0.56 live, 2026-08-24, llm-wiki named as first consumer); gate width (Q1) still open. A optional for deep access, B superseded, C2 obsolete.
Mode: Builder

## Problem Statement

The operator wants to reach the wiki from anywhere, not only on the Mac that hosts the vault — preferably via MCP. Today every consumption path is strictly local: the `use-llm-wiki` skill discovers the vault on disk and shells the `wiki` CLI; the desktop app spawns the same CLI over `--json` seams; mobile participation is intake-only (iCloud file drops). There is no server process anywhere in the engine — the only listener in the repo is the ephemeral Google-OAuth loopback (`scripts/core/google_oauth.py:198`).

The explicit worry: does remote access require a second project (`llm-wiki-server`), and can the engine grow this without losing its core (file-native, local-first, no server, engine–vault split)?

## What Makes This Cool

Any Claude session on any machine — and optionally claude.ai on the phone — can ground itself in the operator's compiled self-knowledge: the index, the hard facts, the entity pages, even the `wiki query` agent. The wiki stops being a single-desk tool and becomes the operator's ambient memory for every agent they run, without the corpus ever moving off their machine.

## Constraints (verified in repo + web, 2026-08-24)

- **Engine–vault split, update-only distribution.** Engine code reaches vaults only via `wiki update` (git pull + `uv sync`); new deps must be declared in `pyproject.toml`; new config knobs require a `migrate_config_keys.py` entry in the same commit (CLAUDE.md hard rule).
- **Machine seams already exist for exactly this consumer class.** `query --json`, `doctor --json`, `menu --json` (bash wrapper `wiki`:622-648), `triage list --json`, `usage --json`, `collect --list --json` were built as "desktop app / agents" seams (C07). An MCP surface is a third consumer of this contract, after CLI and desktop — with one honest exception: serving article bodies and the raw index has **no seam yet**; those two reads are new, thin loaders over existing helpers (`read_wiki_index_compact` in query.py:136, the frontmatter grammar), and they are the code that must be secured.
- **Pure-read vs side-effect commands are already mapped.** Pure: doctor --quick, menu, usage, triage list, correct/take list/show, links, dedup --suggest-only, health-trends --dry-run, config get. Caveats: `query` spends LLM tokens and writes state counters; `lint`/`index` write reports/digests.
- **No semantic index exists.** Retrieval = compact `knowledge/index.md` + hard-facts block + an SDK agent that greps/reads the vault (`scripts/query.py`). An MCP surface inherits this; it does not need (and must not introduce) a vector DB — README non-goals: "not a vector database, not a RAG service".
- **Privacy decisions that bind a remote surface:** raw/ never leaves the personal vault (federation notes); compile is the single knowledge-writer (M027) — no remote path may write `knowledge/` directly; `sensitivity:` frontmatter exists but has **no policy consumer yet**; M027's threat model was explicitly "a single-user private vault" — a network listener changes that model and must bring auth from day one.
- **Host reality.** The vault lives on the operator's Mac (iCloud-synced Obsidian vault). The only scheduling pattern is launchd (bridge LaunchAgent template). A Mac asleep = surface unreachable; acceptable for a wedge, worth naming.
- **Naming footgun.** A `scripts/mcp/` package would shadow the `mcp` SDK import when `cli.py` runs (known stdlib/package-shadow gotcha) — the module must be named e.g. `scripts/mcp_server/`.
- **Client support matrix (2026-08):** Claude Code connects to remote MCP via `--transport http` + bearer header from anywhere (tailnet endpoints fine — the connection originates on the user's machine). claude.ai web/mobile + Desktop **custom connectors require public HTTPS reachable from Anthropic egress `160.79.104.0/23` + `2607:6bc0::/48`** (the older `/21` is deprecated — remove from allowlists) plus OAuth (DCR/CIMD; `static_headers` is beta). SSE transport is deprecated; Streamable HTTP is the standard. Python SDK/FastMCP ship Streamable HTTP + token-verification/OAuth-proxy built-ins.

## Premises

1. **Consumer = the operator and their own agents.** Multi-user/company access is the separate, pending company-brain-federation pitch — explicitly out of scope here.
2. **The wedge is read-only.** Writing stays with compile and sanctioned local channels; at most a later `capture → workspace/inbox` tool (never direct `knowledge/` writes).
3. **The vault stays the local source of truth; raw/ never leaves.** REVISED after operator challenge (2026-08-24): meinkontext MAY become a delivery path — but only for *gated distillate* (knowledge/ articles + hard facts passing a scope/sensitivity gate), pushed one-way from the compile side. meinkontext's own plan of record already names this as Knowledge-KB path (b): "llm-wiki als Quelle anbinden (Server bleibt Registry/Delivery, kompilierter Wiki-Korpus via Import/Sync)" (meinkontext `.ytstack/M017-CONTEXT.md:30` + DECISIONS 2026-07-27; Knowledge-KB is currently a next-milestone candidate in its STATE.md). The original meinkontext pitch consult (2026-07-17) already framed it: "'mein Context' is essentially the serving layer for the personal side of this federation."
4. **The server is an optional adapter.** Off by default, config-gated; the engine, compile loop, and all existing flows behave identically with the flag off.
5. **Client scope decides the exposure tier.** Claude Code-only → tailnet + bearer suffices (no public exposure). claude.ai/mobile → public HTTPS + OAuth is unavoidable (Anthropic egress requirement).

## Landscape (adopt-vs-build)

Nine OSS projects expose Obsidian/markdown vaults via MCP (basic-memory 3.7k★ AGPL w/ own note schema; MarkusPfundstein/mcp-obsidian 4.3k★ stdio-only over the Local REST API plugin; the REST plugin itself now ships a built-in Streamable-HTTP MCP at `127.0.0.1:27124/mcp/`; cyanheads/obsidian-mcp-server adds path-ACLs + read-only switch + HTTP/JWT; lstpsche's Rust server adds BM25 + read-only profiles; others smaller). Two structural mismatches with llm-wiki: they serve **generic file CRUD**, not the engine's curated seams (index/facts/query/triage semantics), and their write tools bypass the single-knowledge-writer discipline entirely. One of them run read-only behind Tailscale is a legitimate 30-minute *experiment*; none is the product.

**meinkontext fit (scanned 2026-08-24).** The operator's context-mcp server (live on dev.meinkontext.de) is a versioned, org-scoped, MCP-only delivery registry: Streamable HTTP + OAuth (DCR/PKCE) + org API keys, Postgres FORCE-RLS + S3 immutable version bundles, @draft→@stable channels, patch-edit write path *explicitly prioritized for future KB workloads*, workspaces waiting for a path-addressed wiki object kind (OQ-B: "braucht das Wiki-Objekt-Kind zuerst"). It has **no KB yet** — "Knowledge follows in later milestones" — and its locked 2026-07-27 decision poses exactly two paths: (a) native KB layer (fulltext/embedding, article kind + graph) vs. (b) llm-wiki as source via import/sync. Crucially, meinkontext already satisfies everything Approach B would have had to build: public TLS endpoint reachable by claude.ai custom connectors, real OAuth, per-principal scoping, audit log. What it cannot offer: live full-corpus interrogation (raw/, daily/, `wiki query` grepping the whole vault) — that stays local by design.

**Readiness — RESOLVED (live-verified 2026-08-24, server v0.0.56 via get_status; meinkontext M019 + M020 complete).** The receiving side is live and llm-wiki is its named first consumer. Binding contract: `docs/PRODUCER-CONTRACT.md` in the context-mcp repo; its executable twin is the "REFERENCE PRODUCER RUN" test (`packages/mcp/src/tools/wiki-tools.test.ts:266`, gates every deploy — on disagreement the run wins). Verified specifics for `wiki publish`:
- `knowledge` kind exists (M019-S01), **excluded from the connect digest by design** — wikis surface as name+count lines; content is reached via server-side FTS `search` + `get_object`. The catalog-flooding concern is solved server-side.
- Lifecycle: `create_wiki {name, slug, description?, managed_by: "llm-wiki"}` once (cooperative marker, not enforced); `write_article {wiki, name, description, content}` per article — every write publishes a new immutable version @stable; **idempotency is the producer's job** (content-hash diff locally, publish only changed); retraction = `delete_object` (archive, auditable, never hard delete); re-`write_article` of the same slug auto-restores; `start_page: true` marks the entry point.
- Conventions: flat global kebab-case slugs (no `/`; prefix like `lw-` for namespacing; unique across the whole catalog), wikilinks normalized to `[[target-slug]]` at compile time (server passes content byte-for-byte), frontmatter verbatim (`compiled_from`, `sensitivity`, `domain` survive), `description` required ≤1024 chars (drives listings/search), secret-value scan rejects writes, publish sequentially (no batch), auth = user-scoped OAuth token per the live-import runbook.

## Approaches Considered

### Approach A: Engine extension — `wiki serve` (read-only MCP, tailnet-first)
  Summary: New `scripts/mcp_server/` subpackage + `wiki serve` CommandSpec entry, built on FastMCP (pinned: its Streamable-HTTP + token-verification built-ins cover this wedge; the official `mcp` SDK is the fallback if FastMCP churn becomes a liability). Tools run **in-process** (imports, not CLI subprocesses). Tool set: `get_index` and `read_article` are *new* thin loaders over existing helpers (`read_wiki_index_compact`, frontmatter grammar); `read_article` takes a knowledge/-relative path or slug and hard-guards via `Path.resolve()` + `is_relative_to(KNOWLEDGE_DIR)` (path-traversal test mandatory); `list_facts`/`get_fact` wrap the facts loaders; `vault_status` returns the `menu --json` payload; `doctor` wraps `doctor --json --quick`. `query` ships only if Open Q2 says yes — it spends LLM tokens, writes state counters, and runs minutes-scale against MCP clients' per-tool timeouts. Transport: Streamable HTTP on a bind-address knob (loopback/tailnet IP); WireGuard encrypts the tailnet path, `tailscale serve` optional for HTTPS; stdio comes free from the SDK for local non-CLI clients. Auth: static bearer token as env `LLM_WIKI_MCP_TOKEN` in `<vault>/.claude/.env` (secrets live in .env, never in config.yaml — so no config key, no migration entry for the token itself). Knobs (config_schema + migration in the same commit): `server.enabled` (default false), `server.bind`, `server.port`, `server.allow_query` (default false). Autostart: LaunchAgent template with `KeepAlive` + bind-retry until `tailscaled` is up (bridge template is the precedent; a resident server needs both). Torn reads while a compile runs are accepted for v1 and documented; a `try_locked` probe on `compile.lock` lets `vault_status` flag "compiling".
  Effort:  M (CC: ~a day incl. traversal-guard tests, token bootstrap, knob migration, PROCESS.md + both infographics)
  Risk:    Low
  Pros:    Single source of truth (in-process reuse of the same loaders the CLI/desktop seams use — no duplicated corpus logic, no version skew); distribution rides `wiki update`; server optional ⇒ core invariants untouched; no public exposure, auth from day one.
  Cons:    No claude.ai/mobile (tailnet invisible to Anthropic egress); availability tied to the Mac being awake; adds the repo's first resident listener (new security surface, even tailnet-only); two reads (`get_index`, `read_article`) are new code to secure, not seam wrappers.
  Reuses:  compact-index + hard-facts loaders, frontmatter grammar, menu/doctor --json payloads, config/migration machinery, LaunchAgent pattern, fail-closed vault guard.

### Approach B: A + public ingress tier for claude.ai/mobile (later deployment profile)
  Summary: Same engine module; add a second exposure tier: Tailscale Funnel or cloudflared to public HTTPS + real OAuth (FastMCP OAuth-proxy or TokenVerifier against an IdP; `static_headers` beta as interim). Requires the sensitivity-policy consumer first (serve only `knowledge/`, honor `sensitivity:` exclusions, per-tool scopes).
  Effort:  M (on top of A)
  Risk:    Medium-high — public endpoint in front of the most sensitive corpus the operator owns.
  Pros:    Phone/claude.ai custom connector works; still one repo — it is a deployment profile of A, not a product; forces the sensitivity-tag enforcement the vault lacks anyway.
  Cons:    OAuth + public-exposure ops burden for one user; Anthropic-egress requirement rules out "VPN-only but mobile" — public means public.
  Reuses:  Everything from A; sensitivity frontmatter (2026-06-10 decision) finally gets its policy consumer.

### Approach C1: Separate `llm-wiki-server` project / cloud copy — rejected
  Summary: Standalone server (own repo, K8s) over a synced copy of the vault.
  Effort:  L   Risk: High
  Pros:    Always-on availability; no listener in the engine repo.
  Cons:    Breaks "without a server" identity and the everything-is-a-file invariant at the product boundary; corpus copy in the cloud violates the privacy posture (raw/ never leaves; redacted-mirror trap); duplicate read logic or awkward engine-as-library dependency ⇒ permanent version skew; this is really the federation product, which has its own pending office-hours.

### Approach C2: OSS stopgap experiment — no engine change
  Summary: Run cyanheads/obsidian-mcp-server (read-only switch, `OBSIDIAN_READ_PATHS=knowledge/`) or the REST plugin's built-in MCP behind Tailscale today.
  Effort:  XS   Risk: Low (if strictly read-only + path-scoped)
  Pros:    Validates the "wiki from my other laptop" UX this week, zero code; informs A's tool design.
  Cons:    File-CRUD semantics only (no index/facts/query seams); second toolchain + Obsidian-running dependency; not the product — throwaway by design.

### Approach D: Export channel into meinkontext (added 2026-08-24 after operator challenge)
  Summary: llm-wiki stays producer + source of truth; meinkontext becomes the delivery layer — its own planned Knowledge-KB path (b). llm-wiki side: a `wiki publish` producer that pushes gated distillate one-way after compile — `knowledge/` articles + hard facts that pass a scope/sensitivity gate — to meinkontext via its existing MCP write tools (`add_object`/`update_object`; patch-edits were designed there for exactly this KB workload; write tools need a user-principal OAuth token, per the live-import runbook pattern). Delta detection by content hash (both sides are already content-addressed/idempotent). First export runs a human approval walk (M027 machinery) — fail-closed, like the federation channel design. meinkontext side (NOT this repo's work, its own milestone): article/knowledge object kind, retrieval over content, workspace selection — the open (a)-vs-(b) decision lives in its plan-milestone.
  Effort:  M on the llm-wiki side (producer + gate + approval walk reuse); meinkontext side is its own milestone.
  Risk:    Medium — a curated subset of personal distillate lives in the cloud (own stack: OVH DE, RLS, audit; but cloud is cloud). The gate design is the load-bearing piece.
  Pros:    Always-on availability (no Mac-awake problem); auth/OAuth/public-TLS already built and live — claude.ai custom connectors work against dev.meinkontext.de TODAY, which kills Approach B entirely; every agent runtime the operator uses already speaks to meinkontext; versioned + auditable delivery; unblocks meinkontext's "einziges Wort des One-liners ohne Milestone"; retrieval (fulltext/embedding) becomes meinkontext's concern — llm-wiki's no-vector-DB invariant stays intact at home.
  Cons:    Not the full corpus — no raw/, no live vault greps, no `wiki query` agent remotely; staleness = compile + publish cadence; requires the scope/sensitivity gate to exist first (it has no policy consumer yet); cross-project coordination (two repos, two milestones, explicit tasking per REGEL #2).
  Reuses:  compile as the single distiller; M027 approval-walk machinery; `sensitivity:` frontmatter axis; federation-channel design ("distilled flows up, never raw"); meinkontext's entire auth/versioning/delivery stack.

## Recommended Approach

**Two lanes, both engine-side extensions — never a separate `llm-wiki-server` project.**

- **For "reach my knowledge from anywhere": D — the meinkontext export channel.** It is the answer both projects' own decisions already point at (meinkontext Knowledge-KB path (b); federation-channel design here). It gets always-on availability, finished auth, and claude.ai custom-connector support without llm-wiki growing a public endpoint — which **supersedes Approach B entirely**. The vault stays sole source of truth; only gated distillate flows up; raw/ never leaves.
- **For "deep corpus access from another machine" (if that need is real): A — `wiki serve`, tailnet-only.** Optional, deferrable; C2 is a cheap way to test whether the deep-access need exists at all before building it.

The original either/or ("eigenes Projekt vs. Erweiterung") dissolves: the *server half already exists* — it's meinkontext. llm-wiki's half is a producer (`wiki publish`), which is exactly the kind of module the engine grows all the time. The separate-repo option remains wrong for the same reasons as before (duplicate logic, version skew, no own storage or release cadence).

Sequencing note (REGEL #2): the llm-wiki side (gate + publish producer) is decided and built here; the meinkontext side (knowledge object kind, retrieval, (a)-vs-(b) decision) belongs to that project's own plan-milestone and needs its own explicit tasking.

## Success Criteria

Lane D (export channel):
- After a compile + publish cycle, an agent on ANY machine (incl. a claude.ai custom connector) answers a personal-context question from meinkontext-served articles/facts — Mac may be asleep.
- Nothing outside the gate ever leaves the vault: no raw/, daily/, workspace/ content and no `sensitivity:`-excluded article reaches meinkontext, verified by gate tests; first export requires an explicit human approval walk.
- Publish is one-way and idempotent (content-hash delta); deleting/retracting an article locally retracts it upstream on next publish.

Lane A (if built):
- From a second machine: `claude mcp add --transport http` + bearer → a Claude session answers a personal-context question using `get_index` + `read_article`, with **zero vault writes, period** (deterministic reads touch nothing; only an explicitly enabled `query` tool may bump `.wiki/state/` counters).
- With `server.enabled: false` (default), the full test suite and all existing flows behave identically — flag off means the feature does not exist.
- **No file content outside `knowledge/` is served by any tool** (raw/, daily/, workspace/, reports/, .wiki/, .claude/, .obsidian/ — the boundary is positive, not a denylist), verified by path-traversal tests. `vault_status`/`doctor` return derived status JSON, never file bytes.
