# M033-S05-T04 -- Task Plan

**Summary:** The desktop side of the contract. `desktop/` validates its engine-payload fixtures
against the same `docs/contracts/*.schema.json` in vitest (`ajv`), and `src/lib/actions.ts`
keeps its hand-written types, with a test that fails when the schema gains a field. The schema
size settles CONTEXT open question 2.

## Files

- Modify: `desktop/package.json` + `desktop/package-lock.json`: `ajv` (8.20, draft 2020-12 via
  `ajv/dist/2020`) as a dev dependency, through `npm install --save-dev`.
- Create: `desktop/src/lib/contract.ts` (test support, never imported by the app). It loads
  the two schema files from the repo's `docs/contracts/` with `node:fs`, compiles them with ajv,
  and exports `validateMenu` / `validateDoctor` (returning error strings) plus the parsed
  schemas.
- Create: `desktop/src/lib/contract.test.ts`, with four checks:
  - `ACTION_SCHEMA` equals both schemas' `schema` const.
  - The engine's oracle goldens (`tests/golden/oracle/menu.json`, `doctor-quick.json`, real
    output on the fixture vault) validate under ajv. That is the second validator next to
    pytest's `jsonschema`.
  - The goldens go through `parseMenu` / `parseDoctor` with nothing dropped.
  - The field inventory: for each payload object the app consumes (`StatusJSON`,
    `SuggestionJSON`, `ActionJSON`, `CheckJSON`), the schema's property names equal a list in
    the test. A field the engine adds fails here until the desktop decides whether to read it.
- Modify: `desktop/src/vault/menu.test.ts`. Its representative `payload()` is already a full
  schema-2 payload; one test asserts it validates.
- Modify: `desktop/src/vault/doctor.test.ts`. The representative payload becomes a full
  envelope (`vault`, `engine_revision`, `summary`) and every check carries every key, `null`
  where the engine sends `null`. One test asserts it validates. The fallback fixtures (a check
  without a `title`, an unknown schema) stay partial on purpose and say so.
- Modify: `.ytstack/DECISIONS.md` (open question 2 decided) and `.ytstack/M033-CONTEXT.md`
  (the question struck through), plus `desktop/README.md`, which gets a line on the contract
  tests.

## What this does

Engine and desktop validate against the same two files: pytest with `jsonschema` (T03),
vitest with `ajv` (this task). A desktop fixture that claims to be engine output can no longer
take a shape the engine never emits. The engine's own goldens run through the desktop's
parsers.

**Decision on open question 2: hand-written types plus an inventory test, not generated
types.** The schemas are small: two documents, seven object types, at most nine properties.
The app's types are normalised views, not mirrors of the payload. For example, `DoctorCheck`
carries `dispatchArgs` in camelCase plus the parse-time fallbacks, and `DoctorResult`
aggregates the checks. Generated payload types would add a codegen step and a dependency
while the parsers would still map raw to normalised. The inventory test gives the same drift
signal at no cost: a new engine field fails a desktop test until someone decides to read or
ignore it.

`scripts/shots/fixtures.cjs` is out of the validation's reach on purpose. It holds the
renderer's parsed state (`DoctorResult`, `MenuResult`), not engine payloads, which is a
deviation from the task line.
