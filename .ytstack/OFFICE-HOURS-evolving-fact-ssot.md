# Design: Evolving-Fact SSOT

Generated by /office-hours on 2026-06-13
Branch: main
Repo: lx-0/llm-wiki
Status: DRAFT
Mode: Startup (intrapreneurship / pipeline-quality)

## Problem Statement

The wiki has no enforced, recency-correct, per-entity single-source-of-truth for
facts that change over time. The SSOT layer (the M005 `## State` block) is only
partially materialized, does not self-heal, is fed by the wrong freshness signal,
and new substrate values are never reconciled against it. Result: when a value
evolves (ADN order volume 174k → 230k → 256k), agent recall grabs whichever copy
it happens to hit — a coin-flip.

This surfaced two ways: Sidney reported his agent is "verunsichert" which figure
is current (no source marks the old number outdated); and Alex's own
`knowledge/projects/adn-ki-programm.md` is `type: project` but has no State block
at all — the figure lives as hardcoded prose at four sites, all reading 230k.

## Demand Evidence

- Alex's own daily driver: recall of a changing number is untrustworthy in his
  live vault. Not hypothetical — the ADN page is the concrete instance.
- Independent second report: Sidney hit the identical failure on his own vault
  ("174k oder 230k oder 256k … wäre Glückssache"). Two operators, same defect,
  found independently.
- Scope is measured, not guessed: in lxw, 37 of 100 entity pages (20 projects +
  17 people) carry no `## State` block at all.

## Status Quo

The manual correction path exists (`wiki correct` → `knowledge/facts/`, overrides
raw at compile + query) but is **dormant** — Alex's own words: "ich nutze selten
den wiki fact process." So the wiki's correctness for evolving facts rests
**entirely** on the automatic pipeline (compile + dream). There is no human safety
net catching wrong values. Today that automatic pipeline:

- does not migrate pre-M005 atomic pages → 37 pages never get a State block;
- maintains State (where it exists) from per-source distill with no recency logic;
- tiers substrate freshness by `path.stat().st_mtime` (ingestion time), not content
  date — so a late-ingested old email can overwrite current State backwards;
- never compares a new substrate value against the current State value.

## Target User & Narrowest Wedge

**User:** the operator (Alex, Sidney) and every agent given wiki access — anyone
who asks the wiki for a fact that has a current value.

**Wedge decision (Q4):** operator chose **full scope A+B+C+D**, reasoned from the
dead manual path — if no one corrects by hand, the automatic path must be
trustworthy on its own, which makes reconcile (C) the core, not a fast-follow.
Accepted, with one challenge folded into sequencing (see Recommended Approach):
build A+B first so C is designed against State blocks that actually exist.

## Constraints

- Engine→vault: code/prompt changes ship via commit → push → operator `wiki update`.
  Never `cp` into the vault. Config-key changes require a migration in the same commit.
- `raw/` is immutable / LLM-read-only. Any contradiction surface lives in
  `knowledge/` or `.wiki/`, never re-entering `raw/`.
- Email substrate is batched per-sweep (one file = many emails of different dates),
  so content-date tiering is clean for per-item substrate (calendar, meetings,
  voice) but needs per-block dating for email — a known sharp edge.
- Editable prompts (`prompts/compile_main.md`, `prompts/dream_entity.md`) are the
  primary surface for A and C; `scripts/dream.py` for B.

## Premises

- **P1 (load-bearing):** the M005 State+Timeline shape is the right SSOT home for
  evolving entity facts. If false, the whole milestone is mis-aimed. Evidence for:
  it already works on dreamed pages (e.g. `stadt-bad-nauheim-ki-programm`).
- **P2:** the manual fact path will stay dormant. Don't design a solution that
  assumes the operator will run `wiki correct`.
- **P3:** "freshness" must mean content-date, not ingestion-date. Holds for
  per-item substrate; email is the exception that needs explicit handling.
- **P4:** a contradiction surface only earns its keep if it doesn't fire on every
  number that appears twice. Signal-to-noise is the design risk for C.

## Approaches Considered

### Approach A: A+D only (cheapest) — REJECTED as the wedge
Materialize State everywhere (compile migrates atomic→two-layer) + instruct
consuming agents that State is authoritative. ~1 day. Rejected: builds a State
block that *looks* authoritative but whose value still comes from per-source
distill with no recency logic — with the manual path dead, the operator would
trust a value that's still a coin-flip. Worse than today's healthy mistrust.

### Approach B: A+B+C+D sequenced (RECOMMENDED)
Same end-state as "full," but ordered: A+B foundation → prove in vault → C → D
threaded throughout. Lets C be designed against real State substrate.

## Recommended Approach

**A+B+C+D, sliced by dependency, not built monolithically:**

- **Slice 1 — A (SSOT universal & self-healing):** port the atomic→two-layer
  migration mandate from `dream_entity.md:44` into `compile_main.md` Instruction 3.
  Next compile that touches an atomic person/project page migrates it. The 37
  pages heal without waiting for dream.
- **Slice 2 — B (recency-correct):** tier dream/compile substrate by parsed
  content-date (filename / frontmatter `date:`), fall back to mtime only when
  unparseable. Fix `dream.py:619` + `:550/:554` + `_recency_decay`. Handle the
  email per-sweep batching edge explicitly (per-block date or exclude from the
  "freshest wins" override).
- **Slice 3 — C (reconcile-against-State):** when compile/dream sees a value for an
  entity, compare to the current State value → update if newer/authoritative, else
  log a divergence to a contradiction surface for operator review. Design the
  surface for low false-positive rate (P4).
- **Slice 4 — D (consumption instruction):** the `<knowledge-base>` preamble
  (`hooks/session-start.py`) + `use-llm-wiki` Read tier state that the State block
  is authoritative and scattered prose mentions are not. Cheap; can land alongside
  Slice 1.

## Open Questions

- **C's contradiction surface:** where does it live? Candidates: a sentinel block on
  the entity page (`## Open Threads`-adjacent), a vault-wide `knowledge/facts/`-style
  review queue, or a lint check that surfaces in the dashboard. Avoid `raw/`.
- **What counts as a "contradiction" worth flagging** vs. normal restatement?
  Scalar mismatch on a typed field is clear; prose divergence is fuzzy. Start narrow
  (numeric/typed State fields only)?
- **Email per-sweep dating:** does B need per-email-block date extraction, or is
  excluding batched-email files from the "freshest-wins" override good enough for v1?
- **Does C subsume or feed the existing `wiki correct` machinery?** A detected
  divergence could auto-draft a hard fact rather than a bespoke surface.

## Success Criteria

- Every `type: person|project` page in lxw carries a `## State` block (0 atomic
  stragglers) after a full compile pass.
- A late-ingested old source provably does NOT overwrite a newer State value
  (golden test: ingest an old-dated email asserting 174k after State says 256k →
  State stays 256k, old value lands only in Timeline as superseded).
- Asking the wiki "what's the current ADN order volume" returns one value,
  deterministically, with the State block as the cited source.
- Any unreconciled scalar divergence appears on the contradiction surface for
  operator review (not silently dropped, not silently overwriting).

## Dependencies

- `core.links` resolver (shipped) for any wikilink rewrites in C.
