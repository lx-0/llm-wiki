## Hard rules

- **Config-knob changes are not done until the vault is migrated.** Adding/renaming/removing a key in `scripts/core/config.py` or `config.example.yaml` requires extending `scripts/migrations/migrate_config_keys.py` in the same commit so operator vaults at `<vault>/.wiki/config.yaml` get the new key written in (with the same default). Dataclass-default fall-through is not "the operator's config reflects the change" — it just hides it. Never `cp` into the vault; the migration is the only legal write path.
- **Push-state is verified before it is claimed.** Never assert "lokal / nicht gepusht / schon gepusht / branch ist hinter origin" from "I haven't run push in this session." Auto-push configs, post-commit hooks, parallel sessions, and prior-session actions can produce committed-AND-pushed without the current session knowing. Run `git log origin/<branch> -5` (or `git fetch && git status -sb`) immediately before any push-state sentence, and quote what you saw. "Ich hab nicht gepusht → also nicht gepusht" is a REGEL #1 violation, full stop. Incident 2026-05-16: claimed `f9b02c5` was `lokal, nicht gepusht`; `git push` answered `Everything up-to-date` because the commit was already on origin.
- **Infographics are steady-state portraits, not changelogs.** `docs/architecture.excalidraw` + `docs/overview.excalidraw` describe what the engine IS today — never how it got there. Banned in the canvas: "SHIPPED <month> <year>" sections, milestone-id badges (`M007`, `M008`, …), date stamps next to pills (`(sandboxed 2026-05-15)`), milestone tags inside feature titles (`Vault Dashboard (M003)`). When a new capability ships, fold it into existing structure: extend a pillar's description, add a caption next to the box that owns it, bump a stat-card if the count moved, add a chip to a substrate list. If a feature has no steady-state slot it isn't diagram-worthy — document it in `docs/PROCESS.md` instead. Incident 2026-05-17: both diagrams had grown a "SHIPPED MAY 2026 · M007 — M013" band; reworked out.
- **Infographic edits aren't done until the rendered PNG has been reviewed for overlap AND overflow.** Excalidraw `text` elements have declared `width` + `height` fields that do NOT constrain the visible glyphs to that rect: multi-line text inside a single-line pill spills down through siblings; a monospace string wider than the declared width spills sideways past the card edge with no warning. The diff in `.excalidraw` JSON does NOT tell you whether the result is legible. Three gates before claiming done after any edit to `docs/*.excalidraw`:
  1. **Bbox-overlap scan** every text pair. Fail on any text-on-text overlap >100 px².
  2. **Glyph-width scan** every text element. Estimated rendered width = `max(line_length_in_chars) * fontSize * 0.6` for monospace (`fontFamily: 3`) or `* 0.55` for non-monospace. Compare against the element's declared `width` AND against the containing card's interior width. Fail on any glyph estimate >declared+5. Also check `(y + height) <= card.y + card.height` to catch vertical card-edge overflow.
  3. **Visual zoom-crop review** of every edited region. The full-thumbnail downscale hides 10-20 px collisions; crop ~25% × 25% around each change and view at ≥1600 px wide. The thumbnail is not the review surface.
  Renderer caveat: at `--scale 2` the Chrome canvas-pixel ceiling silently drops content on diagrams >~12 k pixels per side. If a crop comes back missing content, fall back to `--scale 1` — a smaller PNG with all content beats a sharper PNG with missing boxes. Incidents 2026-05-17: (a) `compile.py\n\nWrites knowledge/** only\nsandboxed` as pill text (height 110 in a 60-tall pill) — three siblings underneath got crashed into; caught by overlap scan. (b) `mail · calendar · gmeet · jamie · voice · health · browser · screenshots · youtube · tabs · clippings · html · inbox` as monospace at fs=11 in a 460 px card — estimated 765 px, ran off the right edge; bbox said "fits", glyphs said "no". Wrap to 2 lines or tighten font.
- **Operator-facing URLs are verified before they are sent.** Any URL handed to the operator to click — Google Cloud Console, OAuth API-enable, GCP project pages, vendor dashboards — must be assembled from authoritative local data, not from training memory or a guess. Project ID + project number + API short-name are all locally readable (e.g. `<vault>/.claude/*-oauth-client.json` → `installed.project_id`, `installed.client_id` prefix; engine config; error payload). Read the source, build the URL with the form the operator recognises (named project ID, not numeric), state it once, correctly. No "try this, if it 404s try that". No mixing project-name and project-number forms across messages. If the data isn't locally available, say so and ask — don't probe with the operator's browser as the test harness.
- **Intake is valued by persona-coverage, not signal-density.** When weighing a new substrate/collector, the question is "what otherwise-dark region of the operator's persona does this cover?" — not "how much knowledge per row?". Self-cartography optimizes for completeness-of-portrait; work-substrate (mail/calendar/docs) systematically misses the non-work self (curiosity, leisure, mood), so a low-yield consumption channel that covers that axis can outrank a high-yield redundant one. "It'll clutter" is not a valid objection — `compile-role: source-only` + `daily/`-aggregation already keep low-signal sources out of per-item `knowledge/`. Two guardrails: value scales per *persona-axis newly covered* (Spotify/YouTube-history/podcasts are mostly one axis — diminishing returns stacking them), and ingest only when the synthesis side (dream-cycle / persona entity-page) will actually consume it (else it grows `raw/` without coverage). Full rationale: `.ytstack/DECISIONS.md` 2026-05-22.
